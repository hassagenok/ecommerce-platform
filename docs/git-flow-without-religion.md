# role table:

1. role: main.
* problem solved: Хранит стабильную и готовую к продакшену версию.
* cost: Имеет ограничения на прямой merge изменений.
* owner: Вся команда или release manager.
* failure mode: Когда нестабильная версия кода попадает в main.

2. role: develop.
* problem solved: Позволяет собирать следующую версию от релизной линии.
* cost: Дополнительный merge и синхронизация.
* owner: Команда
* failure mode: долгая жизнь ветки, нестабильная интеграция и конфликты.

3. role: feature
* problem solved: изолирует разработку отдельных задач.
* cost: создание и поддержание веток.
* owner: разработчик.
* failure mode: долгая жизнь ветки, сложные merge, отсутсвтвие локальных проверок.

4. role: release.
* problem solved: стабилизация релиза без остановки разработки.
* cost: дисциплина замороженных веток и время на поддержку этих веток.
* owner: release manager или команда.
* failure mode: вливание новых фитч, вместо исправлений.

5. role: hotfix.
* problem solved: быстрое исправление критической ошибки.
* cost: merge в main и develop.
* owner: ответсвенный разработчик.
* failure mode: не возвращать изменения в одну из стабильных веток (например: develop), расхождение веток.

6. role: tags.
* problem solved: фиксация точной версии для отката и воспроизводимости.
* cost: поддержка дисциплины версионирования.
* owner: release manager.
* failure mode: нет привязки к релизу, сложный откат или сложно воспроизвести версию.

# scheme:

1. release path: feature/* - develop - release/* - main - tag
* после develop и перед release мы должны заморозить features и лишь исправлять ошибки и стабилизировать ветку release, иначе теряется смысл данной дисциплины.
* после release мы исправляем все ошибки, делаем тесты и стабилизируем перед тем, как влить изменения в main.
* Идея release: отделяет стабилизацию релиза от активной разработки.

2. hotfix path return to main: main - bug - hotfix/* - fix, tests, review - main (deploy fix) - tag
2. hotfix path return to develop: main - bug - hotfix/* - fix, tests, review - develop (return fix) - feature line continues.
* Пути не расходятся, после исправление ошибки, прохождения тестов и ревью, изменения должны быть влиты в main и develop, чтобы данный баг не возникал снова.
* Идея hotfix: используется для срочных исправлений в продакшене.

# decision section:

- Git flow для ecommerce-platform:

1. Соблюдаем:
* protected main - защищает стабильную версию, требует PR, review, CI перед merge.
* feature - изолирует задачи и уменьшает риск конфликтов.
* PR review - проверяет изменения до попадения в main.
* make check / CI - автоматически ловит ошибки до merge.
* tags - позволяет фиксировать named release и делать откаты.

2. Что пока лишнее:
* develop - замедляет процесс разработки, так как добалвяет дополнительные merge, но при этом в данном случае не убирает риски.
* long release branches - в маленькой команде или в одиночном пути разрабокти нет нужны в отдельной стабилизации, если нет внешнего QA.

3. При необходимости:
* hotfix workflow - нужен исключительно при критических ошибок в продакшене.

# signals:

1. Несколько команд или разработчиков работают параллельно:
* develop становится полезным как ветка интеграции между feature и main.
* Сигнал: частые конфликты и риск сломать основную ветку.

2. Нужно поддерживать несколько версий продукта:
* release и hotfix помогают выпускать исправления для старых версий без остановки новой разработки.
* Сигнал: появляются клиенты на разных версиях или необходимость backport исправлений.

3. Появляется фиксированный график релизов (release train):
* hotfix становится полезным для быстрых исправлений с обазятельным возвратом изменений.
* Сигнал: критические ошибки в продакшене происходят регулярно.

# Risks of copying Git Flow blindly:

1. Маленький проект с одним разработчиком создает develop, feature/*, release/*, hotfix/*, но релизится вручную раз в неделю без QA window и без старых версий. В итоге разработчик тратит время на синхронизацию веток, а реальный риск не уменьшается.

2. Создание release/* для каждого небольшого изменения, требует процесса заморозки, дополнительных тестов и управления релизной ветки. В итоге замедляет доставку изменений, хотя проект мог бы безопасно выпускать их напрямую через pr и CI.

Вывод: Git Flow должен появляться как решение конкретных проблем, а не как обязательный набор веток. Если ветка не снижает риск и усложняет процесс разработки, её лучше не добавлять.
