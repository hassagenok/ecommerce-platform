# release branch lifecycle:

1. Create from approved base - создаётся ветка release от стабильного состояния develop.
2. Freeze scope - объявляется feature freeze: новые функции больше не добавляются.
3. Allowed changes - в release разрешены только изменения, необходимые для выпуска: исправления багов, обновления версии, документация, мелкие безопасные изменения.
4. Blocked fixes - исправляются критические ошибки, которые мешают выпуску релиза.
5. Checks - выполняются code review, автоматические проверки (CI), тесты.
6. Tag - после успешного прохождения всех проверок релиз отмечается Git-тегом.
7. Merge/back-merge - ветка release сливается в main для публикации релиза, а затем обратно в develop.
8. Close/Support decision - после релиза принимаются решение: удалить ветку release (если не требуется дальнейшая поддержка), оставить её как ветку поддержки.

# hotfix lifecycle:

1. Detect incident - обнаружение критической проблемы в production.
2. Identify release tag / SHA - опредяется, в какой версии произошла проблема: находится соотвествующий tag или конкретный commit SHA, который сейчас развернут в production.
3. Create branch from production line or tag - создаётся hotfix-ветка от текущей production версии.
4. Focused fix - выполняются только необходимые исправления.
5. Review - изменения проходит проверку.
6. Checks - выполняются проверки: автоматические тесты (make check), CI/CD проверки.
7. Patch tag - после успешных проверок создается новый patch-релиз.
8. Deploy - новый patch-релиз разворачивается в production.
9. Backport - исправление переносится обратно в ветки разработки.

# support line table:

1. Line: main.
* Meaning: Основная production line. Содержит код, который соотвествует текущему стабильному релизу.
* Allowed changes: Вливаются только проверенные изменения. Новые features не добавляются напрямую.
* Owner: Release/production team или владелец продукта.
* Close rule: Закрывается только при замене на другую production line.

2. Line: release/1.4.
* Meaning: Временная ветка подготовки релиза к выпуску. Используется для стабилизации релиза перед выходом.
* Allowed changes: Только bug fixes, blocker fixes, docs, versions и другие изменения, необходимые для выпуска. При этом feautes запрещаются после freeze.
* Owner: release owner / команда, которая отвественная за версию релиза.
* Close rule: После выхода релиза, изменения вливаются в main и develop, затем ветка удаляется или переносится как support при необходимости.

3. support/1.3.
* Meaning: Ветка поддержки уже выпущенной старой версии. Используется для клиентов, которые остаются на старой версии.
* Allowed changes: Только исправление критических багов.
* Owner: support team
* Close rule: закрывается после окончания периода поддержки.

# Backport decision checklist:

1. Affected version - определяется, какие версии затронуты проблемой.
2. Severity - оценивается серьезность проблемы.
3. Target lines - определяются ветки, куда необходимо влить изменение (main, develop, release, support)
4. Validation - проверка корректности backport: проходит ли review, make checks, не ломает ли изменения следующую версию.
5. Release notes - пределяется необходимость обновления документации
6. Owner - назначается отвестенный человек за backport.

# failure modes:

1. Fix не попал в будщие версии - исправление сделано только в Production и может возникнуть в будующих версиях.
* Backport rule - переносит fix в develop и другие активные ветки для избежания возникновения бага в будующих релизах.
2. Hotfix создан не от той версии - исправление сделано не на актуальном production.
* Tag/SHA rule - создавать ветку от точного tag или SHA.
3. Баг попал в production после исправлений - означает, что какие-то моменты не проверялись (Недостаточно проверок)
* Review, checks rules - изменение перед влитием должно пройти обязательные local checks, CI, smoke checks, review и только после вливаться в актуальные версии продукта.

# Local checks and release checks:

1. local checks (make check) - быстрые локальные проверки, которые разработчик запускает перед отправкой изменений. В основном это:
* проверка на форматирование в коде.
* линтеры.
* базовые проверки сборки.

2. release checks - более широкие проверки перед выпуском версии. В основном это:
* полный CI pipeline.
* тесты интеграции (integration tests), security tests, regression tests.
* проверка миграций и совместимости.
* ручные тесты
* approval от отвестенных лиц.
